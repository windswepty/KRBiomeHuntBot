## 이미 밟은 지뢰

- **매크로 홍보 링크 오인** — 매크로 임베드에는 제작자 사이트 링크가 섞여 있습니다. `roblox_only=True`(기본값)로 로블록스 링크만 보호하고, 나머지는 원문 그대로 둡니다. 이걸 끄면 버튼이 엉뚱한 주소로 연결됩니다.
- **매크로마다 링크 위치가 다름** — 평문 URL(maxstellar) / 마크다운 마스킹 링크(Coteab) / **링크 버튼 컴포넌트**(MultiScope). 세 곳을 모두 훑어야 합니다.
- **비공개 카테고리** — 봇이 카테고리를 못 보면 선택 목록에도 안 뜨고 메시지도 안 옵니다. 그래서 이름·ID로 추가하는 경로를 따로 두었습니다.
- **전원 스위치 의미론** — `/인증시스템` 정지 시 **역할 검사보다 전원 검사를 먼저** 해야 합니다. 그러지 않으면 정지 상태인데 유저가 링크를 못 받습니다.
- **`on_message` 리스너 2개 공존** — `ChatReward`는 `author.bot`으로, `LinkGuard`는 `webhook_id`로 걸러 대상이 배타적입니다.
- **임베드 이미지/썸네일 URL은 건드리지 마세요.** 보호 대상이 아니며 제거하면 임베드 모양이 깨집니다.
- **`to_thread` 도입이 경합을 만듭니다.** 예전 동기 코드는 중단점이 없어서 "우연히"
  원자적이었습니다. 스레드로 넘기는 순간 읽기→수정→쓰기가 전부 깨집니다.
  실제로 사용 인원 집계가 80명 → 1명으로 뭉개졌고, 캐시를 로드한 뒤 **다시 확인**해
  하나의 객체를 공유하도록 고쳐서 잡았습니다.
- **상한(trim)이 JSON 경로에만 걸려 있던 버그가 반복됐습니다.** `link_clicks`와
  `activity_logs` 둘 다 Mongo 경로에는 상한이 없어 영구 누적되고 있었습니다.
  새 로그성 컬렉션을 만들 때 **양쪽 경로 모두** 상한을 거세요.
- **동시 완료 순서는 값의 크기 순이 아닙니다.** 디바운스에 "마지막에 도착한 값"을
  쓰면 20명이 눌렀는데 13명으로 남습니다. 단조 증가하는 값은 **최댓값**을 쓰세요.
- **설정 화면의 드롭다운 설명은 View 를 만들 때 값으로 굳습니다.** 값을 바꾼 뒤
  메시지를 다시 그리지 않으면 켰는데도 '꺼짐'으로 보입니다. 컴포넌트·모달
  상호작용은 `interaction.response.edit_message()` 로 자기를 띄운 메시지를
  고칠 수 있으니, 저장 후 패널을 다시 그리세요.
- **패널 임베드는 명령어와 갱신이 같은 함수를 써야 합니다.** 따로 두면 한쪽만
  고쳐져 다시 어긋납니다.
- **상수는 쓰는 곳보다 먼저 정의하세요.** `QUEST_PROGRESS_TTL_DAYS` 를 파일
  아래쪽에 뒀더니 인덱스 생성 시점에 `NameError` 가 나고, 그게 `try/except` 에
  삼켜져 **TTL 인덱스가 조용히 안 만들어질** 뻔했습니다.
- **`ObjectId` · `datetime` 을 문자열로 뭉개면 복원이 조용히 망가집니다.**
  TTL 인덱스는 BSON Date 를 요구하므로, 타입이 달라지면 데이터가 영영 안 지워집니다.
  백업은 `{"$oid":...}` `{"$date":...}` 형태로 타입을 보존하세요.
- **봇이 켜진 채로 복원하면 `delete_many` 와 `insert_many` 사이에 봇이 끼어듭니다.**
  `_id` 가 겹쳐 E11000 이 나고 **복원이 중간에서 통째로 멈춥니다**
  (users 1,236건 중 353건만 들어간 채 멈춘 적이 있습니다).
  `bulk_write(ReplaceOne, upsert=True)` 를 쓰면 몇 번을 돌려도 같은 결과가 됩니다.
- **`--wipe` 는 지우고 넣는 게 아니라 넣고 지우는 순서여야 합니다.**
  반대로 하면 중간에 실패했을 때 데이터가 빈 채로 남습니다.
- **`backups/` 에는 형식이 다른 파일이 섞입니다.** `/백업설정` 이 내려주는
  `users-*.json` 은 포인트 전용입니다. 이름순으로 최신 파일을 고르면 그걸 집습니다.
  수정 시각으로 고르고, 형식을 검사하세요.
- **디스코드 API는 기본 User-Agent를 막습니다.** `urllib` 의 `Python-urllib/3.x` 로
  토큰 교환을 시도하면 Cloudflare 가 **403 / error code 1010** 으로 끊습니다.
  OAuth 가 통째로 실패하는데 원인은 로그에 안 보입니다. UA 를 명시하세요.
- **`urllib` 예외 계층에 구멍이 있습니다.** 응답을 **읽는 중**에 나는
  `TimeoutError` `RemoteDisconnected` `IncompleteRead` `SSLError` 는 `URLError` 로
  감싸지지 않습니다. `except URLError` 만 두면 Flask 500 이 뜨고 진단 로그도 안 남습니다.
  `OSError` + `http.client.HTTPException` 까지 잡으세요.
- **Flask 는 GET 라우트에 HEAD 를 자동으로 붙입니다.** 디스코드·카카오톡의 링크
  미리보기가 HEAD 를 날려 **1회용 토큰을 먼저 소비해 버렸습니다.**
  유저가 누르면 이미 죽어 있습니다. HEAD 는 204 로 막으세요.
- **OAuth 왕복 예산(600초) > 토큰 수명(90초).** 신원 확인에 **성공하고도**
  "만료되었습니다"가 떴습니다. 게이트로 내보내기 직전에 `extend()` 로 늘립니다.
- **만료 판정은 정리(purge)보다 먼저 조회해야 합니다.** 순서를 바꾸면 방금 만료된
  토큰이 이미 지워져 "만료됨" 대신 "유효하지 않음"으로 안내됩니다.
- **`roblox_created_at` 은 유닉스 타임스탬프(int)** 입니다. ISO 문자열이 아닙니다.
  계정 나이 조건을 붙일 때 문자열로 파싱하면 안 됩니다.
- **로블록스 앱은 심사 전 100명 제한**입니다(문서 확인. 예전에 이 문서가 10명이라고
  적어 두었던 것은 틀린 값이었습니다). 승인 전에 `require_roblox` 를 켜면 그 뒤
  유저부터 인증을 못 받습니다. OAuth 미설정 시 켜지지 않도록 막아 두었지만,
  **심사 여부까지는 코드가 알 수 없습니다.**
  **2026-09-05 에 승인되어 지금은 제한이 없습니다.**
- **슬래시 명령어는 전부 `@app_commands.guild_only()` 여야 합니다.**
  DM 에서는 `interaction.guild` 가 `None` 이라 길드를 쓰는 순간 죽습니다.
  실제로 `/출석` 이 그렇게 터졌고, 27개 중 26개가 같은 상태였습니다.
  방어 코드를 명령어마다 흩뿌리는 것보다 **디스코드가 DM 목록에 아예
  띄우지 않게** 하는 편이 짧고 확실합니다.
  **Cog 클래스에 붙이면 안 됩니다** — discord.py 2.7 에서 클래스 속성은
  설정되지만 명령어로 전파되지 않아, 붙였는데 안 걸린 상태가 됩니다.
  `@app_commands.command(...)` **바로 아래**에 명령어마다 답니다.
  `tests/rules.py` 가 빠진 것을 잡습니다.
- **연동 명단 검색어는 반드시 `re.escape` 하세요.** 안 하면 `.*` 한 글자로
  명단이 통째로 덤프되고, ReDoS 도 열립니다.
- **레거시 유저 문서 191건** (`_id`가 user_id인 옛 형식)이 아직 있습니다.
  마이그레이션 경로를 지우지 마세요. 그리고 `replace_one`으로 옮기면 그 사이
  적립된 포인트를 덮어씁니다 — 반드시 `$setOnInsert`를 쓰세요.
- **`tasks.loop` 은 예상 못한 예외가 한 번 나면 영구히 멈춥니다.**
  재시도도 알림도 없고, **프로세스는 멀쩡해서 호스팅도 감지하지 못합니다.**
  자동 백업이 몇 달간 한 번도 안 돌아도 아무도 모릅니다. 새 주기 작업을
  만들면 반드시 `@루프.error` 에 `health.revive_loop()` 를 붙이세요.
  `restart()` 는 **이미 끝난 태스크에는 아무 일도 하지 않습니다** —
  `start()` 를, 그것도 죽어가는 태스크 밖에서 불러야 합니다.
  그리고 `@루프.error` 데코레이터는 **루프 정의 뒤**에 와야 합니다.
  `cog_unload` 가 루프보다 위에 있어서 거기 붙이면 `NameError` 가 납니다.
- **View 를 여러 화면이 함께 쓰면 버튼도 화면을 알아야 합니다.**
  `QuestChannelView` 는 랜덤 채널 후보와 공동 목표 안내 채널 양쪽에 쓰이는데
  해제 버튼이 언제나 랜덤 후보를 지웠습니다. 관리자는 **건드린 적도 없는
  설정이 날아간 것을 모릅니다.** 게다가 후보가 비면 뽑기 풀이 바뀌어
  그날 전원의 퀘스트 목록이 통째로 달라집니다.
- **초 단위 타임스탬프는 ID 가 될 수 없습니다.** 이벤트 id 가
  `e{초}` 라 같은 초에 만든 둘째가 첫째를 말없이 덮어썼습니다.
  이미 쓰는 id 를 피하도록 확인하세요.
- **`required=True` 만으로는 공백을 막지 못합니다.** 디스코드는 공백 문자를
  '입력됨'으로 봅니다. 이름이 `"   "` 인 이벤트가 만들어져 목록에서
  구분할 수 없었습니다. `.strip()` 후 다시 검사하세요.
- **중복 키(E11000)는 이 코드베이스에서 정상 흐름입니다.** 필터에
  '아직 안 받음'을 넣고 `upsert=True` 로 쓰면, 이미 받은 경우 필터에 안 걸려
  삽입으로 넘어가고 같은 `_id` 라 Mongo 가 중복 키를 냅니다. `claim_quest` 는
  **그걸로 중복 수령을 막습니다.** 그러니 `DuplicateKeyError` 만 따로 잡아
  조용히 넘기세요. 통째로 `except Exception` 에 넣고 로그를 남기면, 유저가
  버튼을 두 번 누를 때마다 'DB 오류'처럼 보이는 줄이 쌓입니다.
- **소모된 1회용 토큰은 `peek_owner` 도 없는 것으로 봐야 합니다.** 안 그러면
  신원 게이트가 유저를 디스코드 로그인까지 보내놓고, 돌아온 뒤에야
  "이미 사용된 링크"를 띄웁니다. 죽은 토큰의 수명까지 늘어납니다.
- **`data/` 폴더가 root 소유면 두 가지가 동시에 죽습니다.** 봇은 `ubuntu` 로
  도는데 어느 시점에 `sudo` 로 실행해 폴더가 root 소유로 만들어졌습니다.
  ① `tree.sync()` 지문이 저장되지 않아 **기동마다 전역 동기화**가 나갔고
  (동기화 9회 / 건너뜀 0회 — 기능이 한 번도 동작한 적이 없었습니다),
  ② MongoDB 가 끊겼을 때의 **JSON 폴백도 함께 쓰지 못하는 상태**였습니다.
  겉으로는 완벽히 정상으로 보입니다. 서버를 옮기면
  `ls -ld data` 로 소유자를 확인하세요.
- **그걸 9번의 기동 동안 아무도 몰랐던 이유는 `except: pass` 입니다.**
  쓰기 실패를 조용히 삼켰습니다. 무인 운영에서 조용한 실패는 없는 기능과
  같습니다 — 로그와 상태 임베드 양쪽에 남기세요.
- **호스팅을 옮기면 그 호스팅 전용 환경변수에 기대던 것이 조용히 죽습니다.**
  `current_version()` 이 `RENDER_GIT_COMMIT` 하나만 봤는데, Oracle 에는 그
  변수가 없어 항상 빈 문자열이 되었고 **크래시 루프 경보가 통째로 무력화**된
  채로 며칠이 지났습니다. 지금은 `.git` 에서 직접 읽습니다.
  이전 후에는 "호스팅이 넣어주던 값"을 전부 훑어보세요.
- **배포 서버는 git 저장소여야 합니다.** 손으로 복사하면 무엇이 올라갔는지
  아무도 모릅니다. 실제로 서버의 `.agents/AGENTS.md` 가 Render 시절 버전으로
  남아 있었습니다. 비공개 저장소에는 **읽기 전용 배포 키**를 쓰세요
  (`Allow write access` 는 체크하지 않습니다 — 서버가 뚫리면 저장소까지
  넘어갑니다). 배포는 `git pull --ff-only && systemctl restart` 입니다.
- **Windows 에서 복사한 파일은 CRLF 라 git 이 전부 '수정됨'으로 봅니다.**
  진짜 차이인지 보려면 `git diff --ignore-all-space --stat` 을 쓰세요.
  `--name-only` 는 공백만 다른 파일도 그대로 나열해 사람을 놀라게 합니다.

### 안전장치가 있는데 작동하지 않던 것들

전부 코드가 있고, 주석도 정확하고, 겉보기엔 멀쩡했습니다.
**실행해 보기 전까지는 알 수 없었습니다.** 새 안전장치를 넣으면
반드시 그것이 실제로 걸리는 상황을 만들어 확인하세요.

- **실패를 알려주지 않는 함수는 호출부의 백오프를 지웁니다.**
  `update_goal_message()` 가 429 를 안에서 삼키고 `return` 만 했더니,
  호출부가 정상 반환으로 보고 `goal_backoff.reset()` 을 불렀습니다.
  **방금 건 백오프가 그 줄에서 사라져** 차단 중에도 계속 두드렸습니다.
  주기 갱신 함수는 `upsert_status_message()` 처럼 **bool 을 돌려주고**,
  호출부는 `if ok:` 일 때만 백오프를 풀어야 합니다.
- **`os._exit()` 앞에서 메모리에 기록하면 아무것도 남지 않습니다.**
  `record_restart()` 가 메모리에만 써서, 다음 기동은 늘 이력이 빈 상태로
  시작했습니다. "최근 30분 3회 이상이면 더 기다린다"는 제동이 **한 번도
  걸릴 수 없었습니다.** 재시작을 넘겨야 하는 값은 디스크에 쓰세요.
  (monotonic 은 재부팅을 넘기지 못하므로 벽시계를 씁니다)
- **이미 판정한 조건을 안쪽에서 다시 검사하면 죽은 코드가 됩니다.**
  `should_restart()` 가 레이트 리밋을 이유로 False 를 돌려주는데,
  호출부가 `if should_restart():` 안에서 다시 `rate_limited_recently()` 를
  물었습니다. 그 분기는 도달할 수 없어 **억제가 걸려도 로그가 한 줄도
  안 남았습니다.** 판정 함수는 결과와 **이유를 함께** 돌려주세요.
- **`async with bot:` 뒤에 같은 Client 를 재사용할 수 없습니다.**
  종료할 때 `close()` 가 불려 `_closed` 가 True 로 남고, discord.py 의
  `connect()` 는 `while not self.is_closed():` 라 **즉시 반환**합니다.
  429 재시도 루프가 2회차부터 통째로 무력했습니다. `bot.clear()` 를
  부르세요.
- **누적 실패 카운터는 몇 달 도는 봇에서 반드시 상한에 닿습니다.**
  `revive_loop` 이 성공해도 카운터를 안 줄여서, 몇 주에 한 번 나는
  일시적 오류만으로도 결국 주기 작업이 영구히 멈춥니다.
  **최근 N시간 안의 실패만** 세세요.
- **명령어 지문에 `default_permissions` 를 넣으세요.** 빠뜨리면 권한을
  조여도 지문이 그대로라 동기화를 건너뛰고, **변경이 디스코드에 영영
  반영되지 않습니다.** 이 봇은 권한 지정 명령어가 19개입니다.
- **`asyncio.to_thread` 의 기본 워커는 `min(32, cpu_count+4)` 입니다.**
  2코어 서버에서는 6개뿐인데, 이 작업들은 CPU 가 아니라 **Atlas 응답을
  기다리는 시간**이라 CPU 수로 정할 값이 아닙니다. 80명 동시 클릭을
  재현하니 슬래시 명령어가 426ms 를 기다렸고(3초 제한), 24개로 올리니
  118ms 였습니다. `DB_WORKERS` 로 조정합니다.
- **`fetch_message` + `edit` 은 API 를 2번 씁니다.**
  `channel.get_partial_message(id).edit(...)` 는 조회 없이 바로 고칩니다.
  메시지가 없으면 똑같이 `NotFound` 라 기존 분기가 그대로 동작합니다.
- **403 도 무효 요청으로 집계됩니다.** 채널 권한을 잃은 채 60초마다
  재시도하면 하루 1,440건이 아무 의미 없이 나갑니다. 429 와 같이
  백오프에 넣으세요.
- **감사 도구의 '심각도'를 그대로 믿지 마세요.** 자동 감사가 높음으로
  올린 `guarded_keys` 스캔은 실제 117건이라 비용이 무의미했고,
  '채팅당 스레드풀 포화'는 포화점이 실제 부하보다 훨씬 위였습니다.
  **먼저 재 보세요** — 실 DB 의 건수, 서버의 코어 수, 슬로우모드 설정.
- **오류 핸들러가 오류를 두 배로 만들고 있었습니다.** 상호작용이
  `10062`(3초 초과로 토큰 사망) 나 `40060`(이미 응답됨) 으로 실패하면
  **어떤 응답도 보낼 수 없습니다.** 그런데 핸들러가 안내 메시지를
  시도해 400/404 를 하나 더 만들었습니다. 그 400/404 는 디스코드가
  **무효 요청으로 집계**하는 값(10분 10,000건 → 1시간 차단)이라,
  몰려서 오류가 나는 상황에서 스스로 차단을 당기는 피드백이 됩니다.
  실제로 7일치 로그의 오류 14건이 **전부 두 줄씩** 남아 있었습니다.
  응답 불가 코드는 로그만 남기고 **API 를 쓰지 마세요.**
- **`interaction.response.is_done()` 은 이 프로세스의 기억일 뿐입니다.**
  디스코드 쪽이 이미 응답된 것으로 알고 있으면 `send_message` 가
  40060 을 냅니다. 그때는 `followup` 으로 보낼 수 있으므로,
  **딱 한 번만** 방향을 바꿔 재시도하세요(무한 루프 금지).
- **명령어 27개 중 23개가 응답 확보 전에 DB 를 읽습니다.** 위험해
  보이지만 실측하면 가장 느린 `/포인트랭킹` 이 132ms 로 **3초 예산의
  1/23** 입니다(Atlas 왕복 32ms × 왕복 수). 실제 10062 는 전부
  스레드풀이 고갈돼 **이벤트 루프가 멈춘** 두 구간에서만 났고,
  그때는 맨 앞에서 `defer()` 하던 `/퀘스트` 도 똑같이 죽었습니다.
  **`defer()` 는 느린 DB 를 구해 주지만 멈춘 루프는 구하지 못합니다.**
- **TTL 인덱스는 필드가 없는 문서를 지우지 않습니다.** 인덱스를
  만들어 두고 쓰기 경로에서 그 필드를 안 쓰면 만료는 **영원히**
  일어나지 않는데, 인덱스 목록에는 멀쩡히 보입니다. 실 DB 를 재 보니
  `quest_state` 는 5건 전부, `guarded_keys` 는 117건 전부,
  `protected_links` 는 1,464건 중 473건이 그 상태였습니다.
  `quest_state` 는 코드가 `created` 를 **한 번도 쓰지 않아** 처음부터
  발동할 수 없었고, 나머지 둘은 필드를 추가하기 전의 옛 문서였습니다
  (새 문서는 정상이라 스스로 낫습니다).
  새 TTL 을 만들면 **인덱스와 쓰기 경로를 같이** 확인하세요.
- **주기가 TTL 보다 길 수 있으면 `created` 를 고정하지 마세요.**
  공동 목표는 `reset_days` 로 주기를 정하는데, 그게 TTL(21일)보다
  길게 설정되면 `$setOnInsert` 로 굳힌 `created` 때문에 **진행 중인
  문서가 도중에 지워져 진행도가 조용히 0** 이 됩니다. 활동할 때마다
  갱신해 **마지막 활동 기준**으로 만료시킵니다(이벤트 키와 같은 이유).

### 가짜 Mongo 드라이버를 쓸 때 반드시 맞춰야 할 것

`MONGO_URI=` 를 비운 검증은 **JSON 폴백만** 돌립니다. 실제로 배포되어 도는
Mongo 경로는 한 줄도 실행되지 않습니다. 컬렉션을 가짜로 갈아끼워야 하는데,
아래를 틀리면 **테스트가 거짓 통과합니다.**

- **배열 필드에 대한 스칼라 비교.** Mongo 에서 `{"claimed": {"$ne": x}}` 는
  배열이 x 를 **원소로 갖지 않는다**는 뜻입니다. 배열 전체를 스칼라와 비교하면
  언제나 참이 되어 중복 수령 방지가 통째로 무시됩니다.
- **`upsert` 가 기존 `_id` 를 만나면 덮어쓰지 말고 E11000 을 내야 합니다.**
  조용히 덮어쓰면 위의 중복 방지가 무력화된 채로 통과합니다.
- **가짜 예외는 진짜 `pymongo.errors.DuplicateKeyError` 를 상속해야 합니다.**
  아니면 코드의 `except DuplicateKeyError` 분기가 한 번도 실행되지 않습니다.
- **`insert_one` 은 `_id` 가 없으면 ObjectId 를 만들어 넣어야 합니다.**
  안 그러면 `_id=None` 끼리 부딪혀 없던 E11000 이 납니다.
- **`export_full_payload()` 는 `mongo_db` 에서 컬렉션 목록을 직접 읽습니다.**
  개별 `*_col` 만 갈아끼우면 전체 백업이 텅 빈 채로 '성공'합니다.
- **폴백으로 샜는지 매번 확인하세요.** Mongo 경로가 예외로 죽고 JSON 으로
  넘어가면 결과는 맞게 나오지만 **아무것도 검증하지 못한 것**입니다.
  `using local file` 로그를 세어 0 인지 보세요.

## load_extension 은 모듈을 **새로 만들어** sys.modules 를 덮어씁니다

`tests/notify_mention.py` 를 쓰다가 3건이 이유 없이 실패했습니다. 같은
링크를 두 번째로 쓰는 경우만 멘션이 빠졌는데, 테스트는 매번
`LG._notified_at.clear()` 로 기억을 비우고 있었습니다. 함수를 직접
불러 보면 판정도 멀쩡했습니다.

원인은 **모듈이 두 벌**이었다는 것입니다.

```python
import cogs.link_guard as LG          # ← ①번 인스턴스
await bot.load_extension("cogs.link_guard")   # ← ②번을 새로 만들어 덮어씀
LG._notified_at.clear()               # ①번을 비움 — 실제로 도는 것은 ②번
```

discord.py 의 `load_extension` 은 `sys.modules` 를 확인하지 않고
`module_from_spec` + `exec_module` 로 **새 모듈 객체를 만들어** 등록합니다.
먼저 잡아 둔 이름은 버려진 옛 인스턴스를 가리킵니다.

- **모듈 전역(캐시·기억·플래그)을 만지는 테스트는 `load_extension` **뒤에**
  `sys.modules["cogs.…"]` 로 잡으세요.** 위에서 미리 import 한 이름은
  조용히 다른 객체입니다.
- 그 스위트는 아예 **잡은 모듈이 실제로 도는 것인지**를 첫 줄에서 검사합니다
  (`LG.__dict__ is cog._guard_message.__func__.__globals__`). 이걸 넣어 두지
  않으면 다음 사람도 같은 자리에서 반나절을 씁니다.
- 함수를 몽키패치해 관찰하려 할 때도 같습니다 — 옛 인스턴스에 패치하면
  **스파이가 한 번도 불리지 않습니다.** 그게 이 문제를 찾은 단서였습니다.

## 원본에 멘션이 없으면 "살리기"로는 아무것도 못 합니다

재게시할 때 원본의 멘션을 살리는 코드를 넣고 "이제 알림이 갑니다" 라고
했는데, 매크로 채널에서는 여전히 아무 알림도 가지 않았습니다.

- 그 코드는 **본문에 `<@&역할>` 을 적어 보내는 매크로**에만 해당했습니다.
  MultiScope 는 임베드와 링크 버튼만 보냅니다 — 살릴 멘션이 없습니다.
- 로그에도 아무 단서가 없었습니다. "멘션을 못 울렸다" 경고는 **원본이
  멘션했는데 권한이 없을 때만** 찍히는데, 원본이 멘션을 안 했으니
  24시간 내내 한 줄도 없었습니다. **경고가 없다는 것이 정상이라는 뜻은
  아니었습니다.**
- 임베드 안에 `<@&역할>` 을 적어도 **알림은 가지 않습니다.** 역할 이름으로
  예쁘게 보여서 되는 줄 알기 쉽습니다. 본문으로 끌어올려야 울립니다.
- 채널마다 매크로 출력이 다릅니다. 한 채널에서 되는 것을 보고
  **"이 기능은 된다"고 말하지 마세요** — 어느 채널의 어떤 형식인지까지
  확인해야 합니다.

## 감지 규칙을 만들 때 실제로 뚫렸던 것들

전부 테스트는 통과하는 상태에서 **적대적으로 찔러 보고** 나온 것입니다.
새 감지 규칙을 넣으면 "정상 입력이 잡히는가"만 보지 말고
**"어떻게 하면 안 잡히는가"** 를 먼저 만들어 보세요.

- **보낸 뒤 고치면 그냥 통과했습니다.** `on_message` 는 처음 한 번만
  불립니다. 깨끗한 글을 올린 뒤 수정해서 링크를 끼워 넣으면 감지가
  통째로 우회됐습니다. `on_message_edit` 에서도 같은 검사를 합니다.
  대신 **같은 메시지를 또 고칠 때 다시 알리지 않도록** 최근 처리분을
  기억합니다(자동 삭제가 꺼져 있으면 메시지가 남아 몇 번이든 고쳐집니다).
- **포트를 붙이면 빠져나갔습니다.** `…duckdns.org:443/j/…` 는 주소로는
  똑같이 열리는데 호스트 비교에서 어긋납니다. 한 글자로 우회가 됩니다.
  호스트에서 포트를 떼고 비교하세요.
- **대문자로 적으면 안 잡혔습니다.** `URL_RE` 에 `re.IGNORECASE` 가
  없어서 `HTTPS://…` 는 URL 로 인식조차 되지 않았습니다.
- **호스트는 앞뒤 양쪽을 봐야 합니다.** 앞부분만 비교하면
  `…duckdns.org.evil.com`, 뒷부분만 비교하면 `evil.…duckdns.org` 가
  걸립니다. **정확히 같은지**를 보세요.
- **`needle in link` 같은 부분 일치는 사람을 잘못 지목합니다.**
  `find_issued_to("relay.test")` 처럼 모든 주소에 든 조각을 넘기면
  아무나 짚혔습니다. 지금은 양쪽에서 토큰만 뽑아 정확히 비교합니다.
  **유출자를 지목하는 코드에서 '대충 맞으면 통과'는 사고입니다.**
- **첫 번째만 보고 넘어가면 제일 나쁜 경우를 놓칩니다.** 남의 주소를
  **여러 개 모아** 뿌린 사람이 가장 위험한데, 첫 토큰만 조회하면
  피해자 한 명만 나오고 '모아서 뿌렸다'는 사실이 묻힙니다.
  상한(`MAX_RELAY_TOKENS`)을 두되 **게시된 개수는 그대로** 알립니다.
- **`required=True` 는 공백을 막지 못합니다**(이미 적어 둔 함정인데 또
  밟았습니다). `/개인서버대조` 에 공백만 넣으면 **아무것도 대조하지 않고
  초록색 '문제 없음'** 이 떴습니다. 확인했다고 착각하게 만듭니다.
- **부분 실패를 전부 실패와 같이 다루면 안 됩니다.** 이름 조회가 절반만
  성공했을 때 경고하지 않아서, 낡은 이름으로 대조된 결과를 관리자가
  그대로 믿게 되어 있었습니다. **몇 명을 못 받았는지** 밝히세요.
- **조사용 명령은 반복해서 실행됩니다.** 실행할 때마다 인원수만큼
  왕복하면 느리고 스레드풀을 붙잡습니다. 이름 조회는 10분 캐시하되
  **실패는 캐시하지 않습니다.**

## cog 의 `__init__` 을 앵커로 갈아끼우면 뒤 줄이 다른 메서드로 밀려납니다

`LinkGuard.__init__` 에 주기 작업 시작을 넣으면서, 앵커를

```python
    def __init__(self, bot):
        self.bot = bot
```

까지만 잡고 그 뒤에 새 메서드들을 붙였습니다. 그러자 원래 `__init__` 에
남아 있던 두 줄

```python
        # 같은 메시지를 두 번 처리하지 않도록 최근 처리분을 기억합니다
        self._handled: set[int] = set()
```

이 **맨 마지막에 붙인 메서드(`board_refresh_error`) 본문 안으로** 들어갔습니다.

- 문법 검사 통과, **cog 로드도 통과**했습니다. `python -c "load_extension"`
  검사가 초록이었습니다.
- 실제로는 `self._handled` 가 영영 만들어지지 않아, **웹훅 메시지가 오는
  순간 `AttributeError` 로 링크 보호가 통째로 죽습니다.** 배포했다면

  예약되어야")이었습니다. **보드 기능을 검증하려던 테스트가 보호 자체가

교훈은 둘입니다.

1. **메서드 본문 중간을 앵커로 삼지 마세요.** 삽입할 자리는 메서드의 **끝**

## 백업은 있는데 되돌릴 수 없었습니다 (gzip)

- 포인트 전용 파일을 넣었을 때의 안내는 `documents` 키를 보고 있었는데 실제
  키는 `users` 라 **한 번도 뜬 적이 없었습니다.**

## 워터마크는 로블록스가 링크를 펼치는 순간 사라집니다

매크로가 올리는 것은 **공유링크**(`share?code=…&type=Server`) 입니다.
유저가 버튼을 누르면 로블록스가 **자기 사이트 안에서** 그것을
`?privateServerLinkCode=…` 라는 **다른 주소로 펼칩니다.** 프래그먼트
(`#hbh-…`)는 그 과정에서 떨어져 나가므로, 사람이 눈으로 보고 복사할 수
있는 시점에는 **이미 표식이 없습니다.** 유출자가 지운 것이 아닙니다.

더 나쁜 것은 탐지 쪽입니다. `link_key()` 가 공유링크는 `sh:`, 펼쳐진
것은 `ps:` 로 만드는데 **둘을 잇는 정보가 없어서** 펼쳐진 형태가 올라와도
보호 링크로 알아보지 못합니다. 실측(2026-09-08): `guarded_keys` 136건이
전부 `sh:`, `ps:` 0건, 유출 감지 기록 **0건**. 코드도 설정도 멀쩡한데
**잡을 수 있는 형태가 애초에 들어오지 않았습니다.**

**봇이 직접 펼쳐서 ps 코드를 알아낼 수는 없습니다.**
`apis.roblox.com/sharelinks/v1/resolve-link` 는 로그인된 계정을 요구합니다
(401 — `Server` `ExperienceInvite` `Profile` 전부. XSRF 토큰만으로는 안 됩니다).
공유 페이지를 직접 GET 해도 딥링크 리다이렉트만 나오고 ps 코드는 없습니다.
서버에 로블록스 계정 쿠키를 두면 되지만, **그 쿠키가 새면 계정이 통째로
넘어가고**, 만료되면 무인 운영 중에 조용히 죽습니다. 하지 마세요.

그래서 추적은 **워터마크가 아니라 클릭 명단(`link_usage`)** 으로 합니다.
raw 개인서버 주소는 버튼을 눌러 본 사람만 볼 수 있으므로, **유출자는
반드시 그 링크의 클릭 명단 안에 있습니다.**

> 형태만 보고(`?privateServerLinkCode=` + placeId) 잡는 방법도 있지만,
> **사람이 개인서버를 정상적으로 공유하는 채널이 따로 있으면 쓸 수 없습니다.**
> 이 서버가 그렇습니다. 켜기 전에 반드시 예외 채널을 확인하세요.

## 서명 토큰을 "한 글자 바꿔" 변조 검증하면 간헐적으로 통과합니다

2026-09-15. 신원 게이트 검증(`tests/oauth_gate.py`)을 새로 쓰면서
변조 거부를 이렇게 확인했습니다.

```python
note(G.read_state(st[:-1] + "Z") is None, "변조 거부")   # X
```

전체 검증이 **간헐적으로 한 건 실패**했습니다. 커버리지 모드(2배 느림)
에서만 보여서 처음엔 타이밍 문제로 의심했는데, 아니었습니다.

**base64 의 마지막 글자에는 쓰이지 않는 비트가 남아 있습니다.**
20바이트(SHA-1 HMAC)를 base64 로 인코딩하면 마지막 글자가 2비트만
실제로 쓰이므로, **서로 다른 글자 네 개가 같은 바이트로 디코딩**됩니다.
그래서 "Z 로 바꿨는데 원래 값과 같은 것"이 되는 일이 생깁니다.

실측: 500회 중 **29회가 "변조했는데도 통과"** 했습니다. 쿠키 쪽 같은
검증도 27/500 이었습니다. 두 곳 모두 **가운데 글자를 바꾸도록** 고쳤고
(500회 중 0회), 정말로 바뀌었는지 먼저 확인하는 줄을 함께 뒀습니다.

- **간헐적으로 실패하는 검증은 그 자체가 버그입니다.** 원인을 못 찾으면
  다음 사람이 "가끔 그래요" 하고 넘기게 되고, 그때부터 검증 전체를
  아무도 믿지 않습니다.
- 재현이 안 되면 **반복해서 돌리세요.** 여기서는 40회를 돌려 확인했습니다.
- 변조 검증은 **정말로 값이 바뀌었는지 먼저 단언**하세요. 안 그러면
  "변조본 == 원본" 인 경우가 조용히 통과로 셉니다.

## discord.py 는 503 을 재시도하지 않습니다 — 보호가 조용히 실패하고 있었습니다

  실패가 같은 문장으로 남으면, 로그를 봐도 무엇이 깨졌는지 모릅니다.

## 콜백을 직접 부르는 테스트는 !명령어의 진짜 경로를 못 봅니다 (경고 · 밴 정밀 점검)

`tests/moderation.py` 107건이 전부 통과한 상태에서 정밀 점검(2026-09-25)으로
나온 것들입니다. 전부 **로컬에서는 멀쩡해 보이는** 종류였습니다.

- **!명령어를 콜백으로 부르면 파싱 · 변환기 · 권한 검사 · 오류 리스너를 통째로
  건너뜁니다.** `MemberConverter` 는 `isinstance(result, discord.Member)` 를
  보므로 가짜 멤버로는 그 경로에 들어가지도 못합니다. `tests/moderation_real.py`
  가 메시지를 `bot.process_commands()` 에 넣어 **답장 페이로드까지**
  (`http.send_message` 직전) 봅니다. 봇 루프는 `await bot._async_setup_hook()`
  으로 붙입니다 — 안 하면 이벤트 발송에서 죽습니다.
- **`load_extension` 뒤에는 `sys.modules[...]` 를 고치세요.** 테스트 맨 위에서
  import 한 모듈을 고치면 봇이 실제로 쓰는 모듈에 닿지 않아 검사가 헛돕니다
  (위 절과 같은 이유).
- **디스코드 상한은 로컬에서 안 터집니다.** 자동 처벌 규칙을 1~50회로 받아
  최대 50개가 가능했는데, 지우기 메뉴는 25개까지라 **지울 수 없는 규칙**이
  생기고, 패널 칸이 1024자를 넘으면 `/경고설정` **이 아예 안 열립니다.**
  규칙은 25개로 막고 칸은 나눠 담습니다. 모든 모달 · 메뉴 · 임베드를 **최대
  길이 입력으로** 만들어 규격을 재는 검사가 있습니다.
- **판단 기준이 두 곳에 있으면 어긋납니다.** 경고 DM 을 보낼지(자동 밴이면
  밴 DM 이 대신)와 자동 처벌을 실행할 수 있는지가 따로 판정되어, 밴 DM 이
  꺼졌거나 밴이 막히면 **아무 DM 도 가지 않았습니다.** `auto_rule_blocker()`
  하나를 둘 다 씁니다.
- **'마지막 밴' 은 '지금 밴' 이 아닙니다.** 봇으로 밴 → 해제 → 우클릭으로 다시
  밴이면 봇 기록의 마지막 밴은 **이미 풀린 옛 밴**입니다. 가장 최근 밴/해제가
  해제라면 지금 밴은 봇 밖의 것이라 디스코드의 사유를 씁니다(`current_ban_case`).
- **화면용 이름을 기록하지 마세요.** 검색 후보 이름(`이름 (서버에 없음)`)을
  해제 기록에 넣었더니 이름 검색이 꾸밈을 겹쳐 붙였습니다(`stored_name`).
- **상한 있는 조회로 '전부' 를 처리하지 마세요.** 전체 해제가 최근 200건 안의
  경고만 보고 있었습니다. 유효 경고는 조건으로 직접 찾습니다.

## 날짜를 글자로 비교하면 한 자리 월에서 조용히 틀립니다 (이벤트 퀘스트)

2026-09-26, 관리자가 `2026-9-21 ~ 2026-9-30` 으로 만든 이벤트가 9월 26일에
**'🕒 기간 밖'** 으로 떴습니다. `event_is_active()` 가 `"%Y-%m-%d"` 문자열끼리
비교했는데, 입력 검사(`strptime`)는 한 자리 월·일도 통과시키면서 **저장은
입력 그대로** 했습니다. `"2026-09-26" < "2026-9-21"` 입니다('0' < '9').

- 표시만 틀린 게 아닙니다. `active_events()` 도 같은 판정이라 **진행도가 한
  번도 쌓이지 않습니다.** 채팅을 해도 0 입니다.
- 반대쪽도 틀렸습니다. `9-30 ~ 10-5` 는 '끝이 더 빠름' 으로 **거부**하고,
  진짜 거꾸로인 `10-5 ~ 9-30` 은 **통과**시켰습니다. 전수로 재 보니
  30,240개 조합 중 9,512개(31%)가 틀렸습니다.
- 기존 검증은 날짜를 전부 두 자리로만 넣어서 이 길을 **한 번도 밟지
  않았습니다.** 테스트 입력은 사람이 실제로 치는 모양으로 넣으세요.

**날짜는 `date` 로 바꿔서 비교합니다**(`parse_event_day`). 저장할 때 두 자리로
정리하더라도 판정은 파싱해서 합니다 — 이미 저장된 옛 모양이 있고, 손으로
고친 설정이 들어올 수도 있습니다. 못 읽는 날짜는 **기간 밖**입니다(역할
보상이 영원히 열려 있는 것보다 낫습니다). 검증: `tests/event_period.py`.
